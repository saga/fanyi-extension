# 2026-08-15 工作日志

## 纠正：手机 Firefox 服务端翻译失败的根因（生产日志实测）
用户贴了 `/fanyi/page` 的两段 CF Worker 报错日志：
- `[fanyi/page] error: Colon expected at position 6333 | client=Firefox/153.0 (Android...)`
- `[Pipeline] translateChunks failed after 19313000µs: ... cleanResponse → repairJson → jsonrepair → throwColonExpected`

**结论（推翻此前 CSP 猜测）**：请求确实到达服务端并进入 translateChunks，失败在服务端 LLM 返回的坏 JSON。报错栈 `cleanResponse(gemini.ts) → repairJson(shared.ts) → jsonrepair`，是 **gemini provider 未强制 JSON 输出**导致某 `translated_text` 结构损坏（position ~6333，深度在大数组后半段）。`cleanResponse` 当时无兜底 catch、下游也无故障隔离 → 单个坏 chunk 把整页翻译成 500。默认 provider 是 deepseek（`response_format: json_object` 强约束），用户把扩展 `config.provider` 设成 gemini 才触发。日志里的 Firefox/Android 只是 clientInfo 元数据，不是根因。

## 落地修复（vocal-saga，未提交）
1. `service/shared.ts`：新增 `extractJsonContainer`——截取最外层 JSON 容器（首个 {/[ 到最后一个匹配的 }/]）再交给 jsonrepair，显著提升修复成功率。
2. `translateApi.ts` `processTranslationWithCheck`：解析序列加 extractJsonContainer 步骤；最外层 try/catch，repair 仍失败返回**空 Map**（而非抛错）→ 下游缺失重试/原样渲染。
3. `pipeline.ts` `translateChunk`：service.translate 与 processTranslationWithCheck 各包 try/catch，失败返回空 Map（故障隔离）；缓存写入加 `result.size>0` 守卫，避免空结果污染 KV 缓存。
4. `service/gemini.ts`：translate config 加 `responseMimeType:'application/json'`（从源头杜绝坏 JSON）；`cleanResponse` 的 repairJson 包 try/catch，失败返回 best-effort 而非抛错。
5. `service/deepseek.ts`：末层解析失败返回 best-effort 而非抛错，交由 processTranslationWithCheck 兜底。

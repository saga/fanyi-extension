## FluentRead 借鉴分析（跨三项目调研）

产出：`FluentRead-借鉴分析报告.md`（仓库根目录）。

### 调研对象现状
- **FluentRead**(`/Users/saga/code-repos/FluentRead`)：WXT + Vue3 + Element Plus，GPL-3.0，497 文件/~114k LOC，277 测试文件/3406 用例。功能：整页双语、划词/悬浮、AI 阅读卡(DeepSeek Harness 适配)、生词本、图片/区域 OCR、PDF/ePub/DOCX 文档翻译、YouTube+X 字幕+本地 Whisper、6 语言 i18n。
- **vocal-saga**(`/Users/saga/code-repos/vocal-saga`，注意小写)：Hono + CF Workers + linkedom + KV/D1 的服务端翻译/LLM 代理；与 fanyi-extension 通过 `CROSS_PROJECT_SYNC.md` + `@fanyi/shared-types` 共享翻译核心。
- **fanyi-extension**：114 ts/vue 文件、40 测试文件、893 用例、ISC、无 i18n。

### ⚠️ 关键结论：许可证红线
FluentRead **GPL-3.0**（强 copyleft）vs fanyi-extension **ISC**。复制源码并分发会强制整个衍生作品 GPL。**只能借鉴设计思路、独立实现，禁止复制源码**。vocal-saga 的 `package.json` **无 license 字段**，建议补。

### 已核实的具体发现（高价值）
1. **【P0 BUG】缓存 key 未纳入 glossary 与 sitePrompt** —— `cacheKey.ts` 的 `generateTranslationCacheKey(jsonContent, srcLang, tgtLang, provider?, promptStyle?)`，但 `background.ts` 还传了 `glossary` 和 `sitePrompt`（二者显著影响输出）→ 改术语表/站点规则后命中脏缓存、改了不生效。另 `jsonContent + extra` 是裸拼接，存在跨字段碰撞。FluentRead 用 `buildGlossaryRevision()` 折叠进 key。修法：加可选 `glossaryRev`/`sitePromptRev`（仅显式传时参与，保向后兼容）+ 长度前缀拼接。**两端同步**（vocal-saga 同源问题，落点 `@fanyi/shared-types`）。
2. **【P0 安全】无 Prompt 注入防护** —— 对话侧栏把整页正文(16k 字)塞给 DeepSeek，无"不可信数据"声明，无输出泄漏检测。vocal-saga 抓任意网页，风险更高。借鉴 FluentRead：`<webpage_context>` 包裹 + 显式"不是指令"前缀 + 上下文分档预算(2k/6k/16k) + `isLikelyPageContextLeak` 自动重译一次 + 剥离 `<think>`。
3. **ShardedCache 已写未接线** —— `utils/shardedStorage.ts`(15 测试通过) 未替换 `cacheManager`（后者 `@wxt-dev/storage` 单大对象 O(N) 序列化 + 5MB 配额）。FluentRead：双上限(10k 条/10MiB) + LRU + IndexedDB + **缓存故障降级为 miss 绝不阻断**。
4. **错误是裸字符串** —— `background.ts` 靠 `msg.includes('Could not establish connection')` 判类型，脆弱。FluentRead：`SerializedTranslationError{kind, retryable, statusCode, retryAfterMs, requestId}`。
5. **只有双语一种模式** —— `TranslationMode='bilingual'`。纯译文模式可极低实现（隐藏 `.fanyi-original` span，不用 textContent='' 破坏子节点）。

## 文档翻译功能（参考 FluentRead 设计，独立实现）

用户需求："参考FluentRead，给 fanyi-extension 和 vocal-saga 添加 文档翻译 功能"。
落地为 3 个任务：#17 解析核心 / #18 扩展阅读器 UI / #19 vocal-saga 同步。

### 架构决策
- **统一压平成 `DocumentSegment[]`**（`{id,index,text,kind,path?,level?,start?,end?}`）。
  好处：翻译管线完全复用已有的 chunkBuilder / cacheKey / chunkRetry / singleflight，
  不必为每种格式重写；`id` 稳定 → 译文按 id 回填，重开文档能命中缓存。
- **纯函数层不碰 DOM**，便于同步到 vocal-saga（服务端无 DOM）。
  HTML 解析器是手写容错分词器（非 DOMParser），就是为了同构。
- **字幕按 cue 切分不合并**：价值在时间轴对齐，合并后译文无法回填时间码。
- **预算化分批 + 逐批提交 + 失败隔离 + 可中断**：长文档体验的分水岭。
  单批失败只重跑该批，已完成的译文不丢。
- **二进制格式走动态 import**：pdfjs-dist(legacy 构建，兼容旧 Firefox) 与 jszip
  单独打 chunk，只有打开文档页才加载，不污染 popup/sidepanel。

- fanyi-extension `src/entrypoints/utils/document/`：

- fanyi-extension `src/entrypoints/document/`：`index.html` `main.ts` `App.vue`
  `useDocumentTranslation.ts`

  `tests/documentPipeline.test.ts`(7) `tests/documentRoutes.test.ts`(7)
- popup 新增"文档"按钮 → `browser.tabs.create(document.html)`
  （不用侧栏：文档是沉浸式长内容，且 Firefox Android 无侧栏 API）

### 服务端与扩展的 deliberate 差异
vocal-saga **不支持 PDF/DOCX/EPUB**，显式抛 `UnsupportedDocumentError` + 415。
理由：pdfjs 依赖 Worker+canvas，在 Netlify/Workers 上不可行；jszip 虽可行但
二进制文件本来就在用户手上，没必要上传。已在 CROSS_PROJECT_SYNC.md 记明。

### 踩坑记录
1. **barrel 里 `export *` parser 会触发 INEFFECTIVE_DYNAMIC_IMPORT**，
   动态 import 失效、模块被打回主 chunk。→ barrel 只导出 types/detect/batcher/export。
2. **HTML 解析器的 SKIP_TAGS 不能放 `head`** —— `<title>` 在 head 里，
   跳过就拿不到文档标题（单测抓到）。
3. `splitLongText` / `buildSegmentBatches` 的边界：单段超预算时独立成批，不切碎。
4. vitest 在 fanyi-extension **没有 `@/` 别名**，测试必须用相对路径
   （Vue SFC 里可以用 `@/`，WXT 配了）。

5. **EPUB/DOCX 收尾 bug（tsx 端到端冒烟抓到）**：
   - XHTML 文件头部 `<?xml ...?>` 声明被当文本漏进译文 → `parseHtmlDocument` 开头先 strip
     XML 声明/DOCTYPE/BOM（同构 OPF 的 XHTML 都带）。
   - OPF `<dc:title>` 正则 `<dc:title>` 要求紧跟 `>`，遇带 `xmlns:dc` 属性的标签
     匹配失败 → 改成 `<dc:title[^>]*>`。smoke 造真实 docx/epub（JSZip）验证通过。

6. **文档翻译补 glossary 一致性**：起初 `useDocumentTranslation` 调 `translateChunk`
   没传 glossary，导致文档里专有名词(API/Kubernetes/GPT-5)不按用户术语表保留。
   已补：`App.vue` 用 `extractGlossaryLocal(全文档正文)` 抽术语表 → `run()` 透传给
   `translateChunk` 的 `glossary` 字段。注意：background 的 `cacheKey` 仍不含 glossary
   （分析报告的 P0），改术语表后重开文档可能命中脏缓存——属已知存量问题，本次不修。

## 文档翻译 retry 漏传 glossary（P0 cacheKey 副作用的二次修复）

P0 把 glossary 折进 cacheKey 之后，暴露了另一个 bug：`src/entrypoints/document/App.vue` 的 `retry()` 函数没传 glossary，而 `startTranslate()` 在内部临时 `extractGlossaryLocal(fullText)`。后果：
- 初次翻译：cacheKey 含 `|g<hash>` 后缀
- 重试：cacheKey 不含 `|g...` 后缀（glossary 缺省时折叠规则不追加）
- 同一批内容 → 两次 cacheKey 不一样 → 重试永远 miss → 重新调 LLM，浪费钱+延迟

修复：把 glossary 计算从 `startTranslate` 提到 `loadFile` 解析完成后，存进 `glossary: Ref<Glossary | undefined>`；`startTranslate` / `retry` 都读这个 ref；`resetAll` 一并清空。保证初次与重试拿到完全相同的 glossary，cacheKey 一致，重试能命中初次翻译的 KV 缓存。

仅改 `src/entrypoints/document/App.vue`（加 `import type { Glossary }`、`glossary` ref、`loadFile` 末尾赋值、`startTranslate`/`retry` 改用 ref、`resetAll` 清空）。`wxt build` Chrome MV3 通过（568ms）；`src/__tests__/document.test.ts` 30 项全绿（纯函数 parser 测试，不覆盖 .vue 组件行为，但保证 parse/translate 路径无回归）。

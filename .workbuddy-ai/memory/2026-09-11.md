## 修复：Firefox Android 对话发送按钮溢出屏幕

**现象**：Firefox 移动端，「对话」输入区的发送按钮布局超出屏幕。

**定位**：对话 UI 在 `src/entrypoints/sidepanel/App.vue`（入口 `sidepanel.html`）。
Firefox Android 不支持侧栏（`isSidebarSupported()` 返回 false），对话以**普通标签页**打开。
输入区 `.composer` 是三列 flex：`[JSON 44px] + [textarea flex:1] + [发送 min-w 56px]`，`gap:8px` + `padding:8px 10px`。

**根因**：经典 flexbox **min-content 下限**。flex 项默认 `min-width:auto` = min-content，
而 `<textarea>` 的 min-content ≈ `cols` 默认值（20 字符）。桌面侧栏够宽能吸收，
手机视口（~360–412px）下 textarea 下限 + 两个固定按钮 + gap 超过视口宽度 → 发送按钮被挤出屏幕。

**修复**（仅改 `sidepanel/App.vue` 样式，不动逻辑）：
1. `.input` 加 `min-width: 0;` —— 真正治本，让 textarea 能收缩到下限以下。
2. `.composer` 加 `flex-wrap: wrap;` —— 兜底，任何极端窄屏都不会越界（按钮换行而非溢出）。
3. `@media (max-width:480px)` 内压缩固定控件：JSON `min-w 38/高 40`、发送 `min-w 48/高 40`、input padding 略减，
   尽量让「输入框 + 发送」保持同一行，发送按钮保留可用点击尺寸。

**验证**：`wxt build --mode chrome` + `--mode firefox` 均干净通过（sidepanel CSS 6.17→7.23 kB）；
已确认三条规则都进入构建产物 `output/chrome-mv3-*/assets/sidepanel-*.css`（`.input` 的 `min-width:0`、
`.composer` 的 `flex-wrap:wrap`、`max-width:480px` 块内的压缩规则）。

### 🐛 收尾时发现并修掉第 4 个真实 bug：`translate.html` 的 glossary 传参形态错误

## 2026-09-11 — 修复 docs.langchain.com「标题翻译了、正文没翻译」

**用户报告**：`https://docs.langchain.com/oss/python/langchain/human-in-the-loop`
翻译不成功，截图显示 h1/h2 已变中文，正文段落仍是英文。

### 诊断方法（可复用）

1. `curl -sL -A "<desktop UA>" <url> -o /tmp/page.html`
2. **先数容器，别先读代码**：
   `grep -o '<p[ >]' /tmp/page.html | wc -l` → **8**
   `grep -o 'data-as="p"' /tmp/page.html | wc -l` → **36**
   → 页面正文根本不是 `<p>`。
3. 在 `src/__tests__/` 写一个临时 vitest（jsdom 环境已配好），把 HTML 灌进
   `document.documentElement.innerHTML`，跑真实 `extractBlocks(document)`，
   打印 tag 直方图 + 每个预期段落的祖先链与 `isInsideArticle()` /
   `hasBlockLevelParent()` 结果。**用完即删。**

### 根因

Mintlify 系文档站把 Markdown 段落渲染成 **`<span data-as="p">`**（不是 `<p>`），
外层 `<div class="mdx-content">`，正文根是 `<main>`（无 `<article>`）。

- `<span>` 在 `INLINE_SET` 里，只有 `isInsideArticle() && !hasBlockLevelParent()`
  才可能被单独抓；
- 而 `isInsideArticle()` 只认 `role="main"` 和 `article` 标签 + 文章类名，
  **不认 `<main>` 标签本身** → 恒为 false；
- 结果：**36 个正文段落 0 个被抓**，只有 `DIRECT_SET` 里的标题被翻译。

### 修法（两端手工镜像，blockExtractor 不是 sync pair）

`blockExtractor/rules.ts` 的 `isParagraphLikeElement()` 增加 `data-as="p"` 标记
（新增 `PARAGRAPH_LIKE_ATTRS`）。该函数被 walker 的**两处**引用：
`DIRECT_SET.has(tag) || isParagraphLikeElement(el)` 的 accept 分支，
以及 `hasBlockLevelParent()` —— 所以它既让段落被抓成块，
又阻止段落内 `<a>`/`<code>`/`<strong>` 泄漏成碎片块。

**没有**选择「让 `isInsideArticle()` 认 `<main>` 标签」：那会让 `<main>` 内所有
inline `<span>` 都可能碎片化，风险更大。

**改动文件**（各 2 个）：
- `fanyi-extension/src/entrypoints/utils/blockExtractor/rules.ts` + `src/__tests__/blockExtractor.test.ts`
- `vocal-saga/lib/translate/blockExtractor/rules.ts` + `tests/blockExtractor.test.ts`

## Hacker News 评论翻译（站点规则）—— 2026-09-23 续作

> 日期说明：代码注释 / `CROSS_PROJECT_SYNC.md` 里记为 **2026-09-23**（按机器时钟），
> 本日志沿用会话注入日期 2026-09-11 继续追加，二者是同一条工作线。

需求原话：「针对 https://news.ycombinator.com/item?id=49808023 hackernews 的 comment
是有价值的，添加单独的 rule，需要翻译 hackernews（也就是当前网站）的 comment」。
用户选择：先贴真实 outerHTML（不要我猜结构）+ 增加「抽取期文本剔除能力」。

### 根因（A/B 实测，不是猜的）

HN 整页由**嵌套 `<table>`** 搭成，而 `table/thead/tbody/tfoot/tr/td/th/caption/col/colgroup`
都在 `SKIP_SET` 里 = `FILTER_REJECT` 剪整棵子树 → 抽取结果 **0 块**。
（`SKIP_SET` 的表格剪枝是为**数据表**设计的，见 constants.ts 注释。）

评论正文结构（用户贴的真实 HTML 纠正了我此前的错误假设）：
```html
<div class="comment">
  <div class="commtext c00">裸文本首段<p>第二段</p><p>第三段</p></div>
  <div class="reply">…reply…</div>   <!-- 是 commtext 的**兄弟**，不是子节点 -->
</div>
```

### 新增 3 个 SiteRule 字段（只影响抽取；两端都要有，非 sync pair，手工镜像）

| 字段 | 作用 |
| --- | --- |
| `excludeFromTextSelectors` | 抽取块文本时把命中的子树从文本里剔除 |
| `translateTables` | 不剪 `table` 系标签（走普通容器分支） |
| `blockSelectors` | 命中的元素整体作为一个翻译块（等价 `data-as="p"`） |

**为什么剔除不能复用 `skipSelectors`**：`skipSelectors` 语义是「不单独翻译」≠「文字不该
出现」。GitHub 把 `code`/`pre` 放进去，若连带剔除文本，行内 `<code>` 会让译文变成
"Use to install"。HN 同理：`code`/`pre` 留在 `skipSelectors`，另用
`excludeFromTextSelectors: ['.comhead','.pagetop','.reply']`。两端各加了一个反例守卫用例
（行内 `<code>std::map</code>` 必须留在文本里）。

### 三个踩到的坑（都写进 skill 了）

1. **`FILTER_ACCEPT` 不阻止下钻** —— 源码里「ACCEPT = 不走子树」的注释是**错的**。
   `div.commtext` 整体成块后，内部 `<p>` 又被抓一遍 → 重复译文。
   修法：成块后 `rejectedCache.add(el)` 让后代连坐。
2. **抑制必须带守卫** —— 服务端 `acceptNode` 原本**没有**扩展端那个
   `hasDirectSetDescendant → SKIP` 检查。我加上抑制后，`<li>` 内嵌 `<p>`（arxiv 摘要）
   的子块被连坐删掉，**4 个测试挂掉**。补上守卫后修复。扩展端本来就有这个守卫。
3. **linkedom 解析裸片段会错位** —— `parseHTML('<table>…')` 把 `<tbody>` 挂到 `<html>`
   下（与 HEAD/BODY 平级），`document.body` 是空的 → 抽 0 块。服务端片段必须包成
   完整文档。jsdom 无此问题。

### 顺带做的两件事

- **文本有效性判定改用 `getBlockText`**（不再用 `el.textContent`）：否则「只剩被剔除
  装饰」的包裹层（`div[style="margin-top:2px"]`、顶栏 `<td>`）会被判为有效块，
  译文里冒出 "neilv 0 minutes ago | next [–]" 这种垃圾块。
- **剔除路径下块级子元素间补 `\n\n`**：`textContent` 会把 `<p>a</p><p>b</p>` 拼成
  `"ab"`；整块抓取的多段容器需要保留段落边界，否则译文糊成一整段。

### HN 规则最终形态

`skipSelectors: ['.votelinks','.rank','.score','.subtext','.comhead','.pagetop','.reply','code','pre']`，
`translateTables: true`，`blockSelectors: ['.commtext','.titleline']`，

## 上述两项「未修」的收尾 —— 2026-09-23 续作

### 1. ZWSP 等不可见边缘字符（Mintlify 标题锚点）

**根因**：Mintlify 每个标题里都有一个 hover 才显示的锚点 `<a class="…opacity-0…">`，
其唯一文本就是 **U+200B**（外加一个图标 `<div>/<svg>`）→ `textContent` 得到
`"\u200bInterrupt decision types"`。真实 LangChain 页面上 **14 处**。

**为什么 `trim()` 无效**：`trim()` 只去 Unicode **White_Space**；而
U+200B/200C/200D/2060/FEFF/00AD 都是 **Cf（格式）字符**，不在 White_Space 里，
所以 `"\u200b标题".trim()` 原样返回。**只能显式列出。**

**修法（单一收口点）**：新增 `normalizeBlockText()`，把块文本的「出口」从裸 `trim()`
全部改为它。正则 `PATTERNS.INVISIBLE_EDGE` = 一个字符类
`[\s\u200B\u200C\u200D\u2060\uFEFF\u00AD]`，配 `^…+|…+$`，一次 `replace` 同时完成
trim + 零宽字符清理。

**只去边缘，绝不做全局替换**：ZWNJ/ZWJ 是**语义字符**（波斯语 `می\u200cخواهم`、印地语、
emoji ZWJ 序列 `👨\u200d👩\u200d👧`），全局删会破坏正文。测试里专门有一条用例守住这点。

**四个出口都要覆盖**（漏一个就漏一处）：
1. 扩展 `getBlockText` 快速路径
2. 扩展 `getBlockText` 剔除路径
3. 两端 `getHeadingPath` / `headingStack`
4. 服务端 `extractBlocksFromMarkedHtml`（`el.textContent` 是第 4 个独立出口，容易漏）

**为什么改文本是安全的**：块文本只用于「发给模型 / 去重 / 估 token / 报告」，
**从不用于回写渲染** —— 渲染走 DOM 节点（`applyBlockTranslation` 把原有子节点
搬进 `.fanyi-original`），所以规整文本不影响渲染。

**验证**：对真实 1 MB 页面 `/tmp/langchain-hitl.html` 跑探针 →
`62 blocks / 10 headings / blocks with leading invisible char: 0 / headingPath entries: 0`，
标题全部干净（`"Human-in-the-loop"`、`"Interrupt decision types"`、…），修复前是 14 处。

### 2. 服务端 walker 的 counter 记账

服务端 `walkNode` 的 `DIRECT_SET || isParagraphLikeElement` 分支原本**不累加 counters**，
`accepted` 长期严重偏低（HN 6 块只报 `accepted=1`）。

**动手前先确认是纯诊断量**：`noiseRatio` / `extractionQuality` 只出现在一处
`console.log` 和临时脚本里，**没有任何分支依赖它** → 对齐是安全的（若被用于分支就不能动）。

**修法**：补上扩展端本来就有的守卫与记账
（`hasDirectSetDescendant → skipped++ / FILTER_SKIP`；接受 → `rejected.add(el); accepted++`；
其余 → `skipped++`）。HN fixture 上 `accepted` 由 `1 → 7`，两端各加一条回归用例。

### 故意不移植的分歧（记录在案）

扩展端该分支还有 `hint < 0 → SKIP` 的软评分闸门（`computeSoftHint`），
**服务端没有软评分机制**，故不移植 —— 这是有意的分歧，不是漏改。

### 收尾时发现的第三个问题：fixture 并未真正镜像

`hackernews-item.html` 在两端**并不一致** —— 扩展端 21270 B，服务端 11294 B。
原因：扩展端那份快照是从真实浏览器会话里重新保存的，被注入了页面插桩属性
`data-page-node-id="…"`（几乎每个元素都有），体积翻倍；服务端那份是更早 `cp` 的干净版。
→ **两端测试其实在跑不同的 HTML。**

处理：把扩展端 fixture 里的 `data-page-node-id` 全部剥掉
（`re.sub(r'\s*data-page-node-id="[^"]*"','',html)`），剥完 **11294 B = 服务端那份，byte-identical**。
已验证没有任何测试/抽取器引用该属性。剥完重跑：扩展 HN 5/5、服务端 HN 6/6、扩展全量 997/997。

**教训（已写进 skill）**：镜像 fixture 后必须 `diff -q` 验证，不能假设；从浏览器重新保存快照
会带入插桩属性。

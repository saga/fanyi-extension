## chat mode 基于 DeepSeek 指南的改进

参考 deepseek.com 6 篇指南 + ai-interview-questions 经验，改进 `src/entrypoints/service/chat.ts` 的对话能力：

- **KV Cache 命中遥测（最高价值）**：流式请求加 `stream_options.include_usage=true`；`streamParser.ts` 新增 `parseSSEStreamWithUsage` + `extractUsage` 解析尾帧 `usage.prompt_cache_hit/miss_tokens`；归一化为 `ChatUsage` 回传。因 `buildChatSystem` 对同页是确定性前缀，多轮时 system 前缀命中缓存、输入 token 大幅下降。UI 顶部实时显示"KV 缓存命中 X%"。
- **Abort 中断**：`chatStream` 支持 `AbortSignal`；background `chat` 端口在 `onDisconnect` 时 `AbortController.abort()`；`chat/App.vue` 关闭/卸载时 `port.disconnect()`，背景中断在途流，省配额。
- **JSON 模式（opt-in）**：`ChatOptions.jsonMode` 挂载 `response_format=json_object` 并在 system 追加 JSON 指令；UI 加 JSON 切换按钮（默认关，避免破坏对话自然性）。`chat()` 空内容单次重试（DeepSeek JSON 已知偶发空）。
- **空内容兜底**：`chatStream` 流结束仍为空则抛错提示重试。
- 不适用的指南（已决策跳过）：`chat_prefix_completion`/`fim_completion`（Beta、需 /beta、面向代码补全）；`responses_api`（弃用 previous_response_id/KV key、对 SSE 解析无增益）。`multi_round_chat` 此前已实现（无状态全量历史），保持不变。

验证：`./node_modules/.bin/vitest run` 全绿（893 passed，含 chat.test.ts 5 项）；`wxt build` 通过（1.21 MB）。

## 修复 getPageContext 的 "Could not establish connection" 噪音

现象：`[fanyi:error] [Background] getPageContext error: ... Receiving end does not exist.`（与首问"无法连接到该页面"同源）。

根因：目标标签页无 content script（非 http(s) 页：chrome://、file://、about:、PDF 查看器、扩展自身页），`tabs.sendMessage` 必抛此错。content.ts 本身已正确响应 `extractChatContext`，路由没问题。

改动（`background.ts`）：
- 新增 `isWebUrl(url)`（仅 `^https?://`），`getActiveContentTabId` 改为只返回普通网页标签，非 web 页直接不尝试 sendMessage（避免触发连接错误）。
- `handleGetPageContext` 的 catch：连接类错误（含 "Could not establish connection" / "Receiving end does not exist"）由 `logger.error` 降为 `logger.debug`（用户已在 UI 看到友好提示，不再以 error 刷屏）；其它异常仍 `logger.error`。

⚠️ 踩坑：在 `/** */` 块注释里写了 `matches: ['*://*/*']`，其中的 `*/` 提前闭合了块注释，导致 wxt 的 babel transform 解析报错、dev server 崩溃。已把该注释改成 `//` 行注释规避（`//` 注释不受 `*/` 影响）。教训：块注释里出现 `*/` 子串会提前结束注释。

验证：`wxt build` 通过；dev server 已重启（task eoFQ4v，localhost:3000）。

## 支持本地 file:// 页面（延续"非普通网页"缺口）

承接上一条：用户说"continue"= 接受此前提出的 file:///PDF 改进。PDF 查看器是 chrome-extension 内部页、content script 不可靠注入，故只做 file:// 本地 HTML。

改动：
- `content.ts`：`matches` 由 `['*://*/*']` 扩为 `['*://*/*', 'file:///*']`。
- `wxt.config.ts`：Chrome `host_permissions` 与 Firefox `permissions` 都加 `'file:///*'`（content script 注入 file:// 的前提之一）。
- `background.ts`：`isWebUrl` 由 `^https?://` 扩为 `^(https?|file)://`；`handleGetPageContext` 连接失败时若源标签是 `file://`，提示"请在扩展管理页开启'允许访问文件网址'"。
- PDF 仍不在 scope（不可靠），保持原友好提示。

前提（用户侧动作）：Chrome 须在 chrome://extensions 该扩展卡片开启"允许访问文件网址"，否则 file:// 页仍无 content script、走友好提示分支（已是 debug 级日志）。

验证：`wxt build` 通过（1.22 MB）；`chat.test.ts` 5 项通过；dev server HMR 已载入（manifest 12:20 更新）。

## 手动输入上下文兜底（"任何页面都能聊"）

动机：用户对"此页面已被 Chrome 屏蔽"等场景反复要求"解决"——Safe Browsing 是 Chrome 自身行为无法在扩展里消除，但 chat 本身可绕过：让用户在被拦截/无法读取时手动粘贴正文。

改动（仅 `chat/App.vue`）：
- 新增 `manualMode` / `manualText` 状态。
- `loadContext` 失败路径不再只是 `status='error'`，同时 `manualMode=true`。
- 新增 `applyManualContext()`：把粘贴内容打包成 `pageContext`，进入正常对话流程。
- 模板：error 状态下多出一个黄色 `.manual-context` 块（textarea + "用此内容对话"），可折叠地出现在 banner 与消息列表之间。
- 样式：浅黄底 + 警告色文字，与 error banner 视觉关联但独立。

效果：Chrome 安全拦截页、`chrome://`、`file://` 未授权、content script 未注入等所有"读不到原页"的情形，用户粘贴正文后即可正常多轮对话。`buildChatSystem` 走的是同一个 system 构造路径，KV cache 在手动上下文下也对齐。
